# Audit du site L’Héritage — 10 novembre 2026

## Périmètre et méthode

Le Site GitHub `Vigneron-B` était propre sur `main` (`5d71c18`) avant les changements. Les tests et mesures ont utilisé des serveurs locaux, des bases temporaires et des avatars simulés. Le Site Linux et le bot vivants ont ensuite été contrôlés en SSH, avec des lectures SQLite en mode `ro`. Aucun message Discord ni aucune modification Google n’a été déclenché. Aucune source, donnée ou configuration Linux n’a été modifiée.

L’audit « impeccable » donne **12/20 avant** et **14/20 après** les corrections ciblées : accessibilité 2/4, performance 2→3/4, responsive 3/4, thèmes 3/4, intégrité 2→3/4. Le contrôle de largeur n’a relevé aucun débordement horizontal entre 320 et 1 440 px sur les pages examinées. La direction artistique, les images et les animations ont été conservées.

## Suite demandée — contrats, sondages, accessibilité et profilage

- **Confirmation de clôture.** Un test signé a montré qu’un ACK `applied` était accepté avec un snapshot inchangé. [business_bridge.py](../backend/business_bridge.py) conserve désormais les identifiants confirmés de la semaine et ses archives dans une table du site liée à la commande ; le message envoyé au bot garde exactement son contrat précédent. L’ACK exige une nouvelle archive contenant tous ces dossiers, même si d’autres fiches ont été ajoutées entre-temps. Le test couvre un ACK mensonger, une archive incomplète, une fiche ajoutée entre la demande et l’ACK, le snapshot publié avant l’ACK et sa relivraison. Pour une semaine vide ou une commande mise en file avant cette modification, le protocole actuel du bot ne fournit pas de preuve supplémentaire ; la compatibilité est conservée. Le helper `WebsiteClient.poll`, inutilisé et incapable de fournir le résultat obligatoire, a été retiré de [website_client.py](../connectors/website_client.py). La copie Linux du bot n’a pas été touchée.
- **Sondages métier.** Un test à horloge simulée a mesuré **5 lectures en 6 s** pour une commande en attente sur la page active : 3 par le suivi de confirmation, 2 par le rafraîchissement visible. [secure.js](../static/secure.js) fait maintenant utiliser l’état rafraîchi au suivi lorsque la page est visible et libre ; le même scénario ne produit plus que **2 lectures en 6 s**. Le suivi garde sa lecture propre sur une autre page ou lorsque la vue ne peut pas se rafraîchir. La confirmation et le refus restent annoncés.
- **Accessibilité.** La région `#content` n’annonce plus chaque changement du compte à rebours. Un statut discret annonce le changement de page une seule fois dans [app.js](../static/app.js) et [index.html](../static/index.html), avec la copie GitHub générée synchronisée. À 320 et 390 px, les trois commandes d’en-tête vérifiées — menu, notifications, paramètres — mesurent au moins **44 × 44 px**, sans débordement horizontal. La direction artistique est conservée.
- **Profilage du backend.** [profile_security.py](../scripts/profile_security.py) emploie une base temporaire et un faux Discord. Avant changement, huit lectures de `/api/pages/sales?view=screen` ont donné une médiane de **30,09 ms**, **17 connexions SQLite** et **2 contrôles de permission** par requête. Après suppression du contrôle anticipé uniquement sur les lectures `/api/pages/`, la route vérifie toujours les droits juste avant de lire les données : **14 connexions** et **1 contrôle**, avec une médiane de **31,11 ms**. La différence de latence sur huit essais est du bruit ; le gain mesuré porte sur les lectures de base. Avec une attente simulée de 200 ms sur `member`, un `Security.resolve` prend environ **229 ms** et deux appels concurrents environ **459 ms** après ce changement : le verrou global les sérialise toujours. Le déplacer hors des appels réseau exige une conception de concurrence et des tests de course supplémentaires, car les événements du bot et les modifications de comptes utilisent le même verrou.

Après ces changements : **80 tests Python ciblés** puis **101 tests Python de sécurité et de chargement** après la réduction des contrôles redondants, ainsi que les tests Node de sondage, confirmation, navigateur et reprise, passent. Le test d’intégration avec la sauvegarde Windows du bot n’a pas pu démarrer : `gspread` manque dans le Python local, même si ses transports Discord et classeurs sont simulés. Aucun test n’a appelé le vrai bot, Discord ou Google. Ces nouvelles modifications restent locales ; aucune copie Linux n’a été déployée.

## Suite du 11 novembre — concurrence et preuve de clôture

Le verrou global de [security.py](../backend/security.py) ne couvre plus les attentes réseau Discord. Un verrou par compte empêche deux contrôles simultanés du même membre ; un compteur de génération détecte les événements d'accès du bot pendant l'attente. Après le réseau, la session, le compte et le droit d'accès sont relus sous le verrou global avant toute réponse. Trois tests avec un faux Discord bloquant valident la concurrence entre comptes, la révocation de session pendant l'appel et une mise à jour de membre qui retire le rôle employé. Sur la fixture à 200 ms d'attente, deux comptes distincts terminent ensemble en **266 ms** environ, contre **459 ms** avec l'ancien verrou ; deux requêtes du même compte prennent **598 ms** ensemble. Ces mesures incluent SQLite et l'ordonnancement local. Huit lectures de page utilisent toujours **14 connexions SQLite** et **un contrôle de permission** ; leur médiane de **84 ms** est trop variable pour conclure à un gain de latence.

La clôture de semaine du bot Linux renvoie maintenant le nom d'archive déjà produit par `reset_sales_week_sheet`, y compris après une reprise depuis son journal d'opération. Une copie préalable du fichier a été placée dans `bot_blanchiment/data/backups/`. [business_bridge.py](../backend/business_bridge.py) exige ce nom dans l'ACK signé et vérifie, si la semaine contenait des dossiers, que tous les dossiers initiaux se trouvent dans cette archive. Pour une semaine vide, le nom nouveau dans le résultat durable du bot constitue la preuve disponible : le snapshot seul ne contient aucune archive sans dossier. Les commandes anciennes sans baseline restent compatibles. Le dernier contrôle précédent de la base Linux relevait **zéro remise à zéro en attente** ; aucun ancien ordre n'a été relancé.

La suite complète [test_business_contract.py](../tests/test_business_contract.py) a été exécutée dans un dossier Linux temporaire avec les sources locales du site et le code réel du bot, mais des transports Discord et un classeur local simulés : **14 tests passés**, dont deux clôtures successives (semaine vide puis semaine avec dossier). Les **10 tests** métier propres au bot, **114 tests** ciblés de sécurité et de commandes du site, les **12 tests** du pont métier, et `verify_load.py` sur Linux (**154 requêtes, intégrité et arrêt vérifiés**) passent. Le test de charge a signalé sur Windows une erreur de fermeture du serveur temporaire ; ce problème n'a pas été reproduit sur Linux. Aucun test n'a envoyé de message Discord ni modifié Google.

Le code du Site GitHub et les tests restent locaux dans ce répertoire Git. La source du bot Linux a été corrigée et sauvegardée, mais `blanchimentbot.service` tourne toujours avec le processus démarré le **10 novembre à 11:03:39 CET** : son redémarrage reste nécessaire pour charger le changement. Le Site Linux est distinct et n'a reçu aucun de ces changements ; adapter et déployer son pont métier et sa sécurité à partir de sa propre copie, puis redémarrer `heritage-site.service`. La publication GitHub Pages reste également à effectuer après intégration des changements Git.

## Contrôle des pourcentages de progression

Le bot utilise une division entière pour la progression d'un dossier, alors que les deux copies du site arrondissaient au plus proche. Par exemple, 1 999 999 $ traités sur 5 000 000 $ donnaient **39 % dans le bot** et **40 % sur le site**. Une simple division flottante dans JavaScript donnait parfois **28 % pour 29 % exacts** ; les deux sites utilisent désormais une division entière exacte sur les montants entiers sûrs. Le Site GitHub a été modifié localement ; le fichier distinct du Site Linux a reçu uniquement ce calcul, après sauvegarde privée. Neuf cas de comparaison passent sur chaque copie, y compris une valeur proche de la limite des entiers sûrs.

Le bot Linux pouvait afficher **120 %** pour un dossier entièrement traité avec un surplus, bien qu'il affiche déjà ce surplus à part. Sa progression affichée est maintenant plafonnée à **100 %** ; la ligne du surplus et l'indicateur rouge restent visibles. Son nouveau test simulé et les dix tests métier existants passent. Le processus `blanchimentbot.service` n'a pas été redémarré : le nouvel affichage Discord prendra effet après ce redémarrage. Aucun message Discord ni aucune modification Google n'a été produit par ces tests.
